# FOODIDENTITY 核心功能盘点与迁移影响分。

适用范围说明。- 本报告基于当前仓库结构判断。- `foodidentity` 视为霢要并入主项目的功能源项目。- `AI-FIT` 主项目在本报告中的角色，仅作为前端风格模板和主站 UI 容器。- 本报告不再把主项目现有后端”数据库模型、既。food 能力当作业务模型约束。- 但迁移完成后的正式项目技术架构，必须以主项目为主，不能在运行时依。`foodidentity` 文件夹。- `foodidentity` 的定位是迁移来源与功能参考，不是未来长期保留的子系统；迁移完成后该目录应可被清理。- 本报告聚焦的问题是：`foodidentity` 的核心功能是否”合作为未来正式方案，并以较快”度接入主站视觉层。

判断：- 可行性：。- 合理性：。- 快”落地”：。
原因。- `foodidentity` 本身已经具备完整朢小闭环：
  图像识别 -> 食物匹配 -> 食物选择 -> 餐次记录 -> 当日汇。- 其数据结构”接口设计”前后端交互是同丢套”路下形成的，内部一致”比“接到另丢套旧模型上”更强。- 如果主项目只负责承接 UI 风格，那么迁移的本质就是。  保留 `foodidentity` 的业务与数据方案，把它们重建到主项目抢术栈中，并将前端视觉外观和主站布屢对齐。`AI-FIT`。
## 2. 本次迁移的推荐原。
本次迁移建议明确采用以下原则。
### 2.1 以后端与数据库对。foodidentity 为主

含义。- `foodidentity` 的接口结构”业务流程”数据表设计应作为主基线。- 不以主项目现有后端接口为兼容目标。- 不以主项目现有数据库模型为兼容目标。- 但实现载体必须落在主项目正式后端与正式数据库中，而不是继续引。`foodidentity` 下的服务和脚本。
直接影响：- 后端迁移应优先保。`foodidentity` 。API 语义。- 数据库应优先保留 `foods / meal_records / meal_items` 这一套业务模型。- 迁移后的代码、表结构、配置”环境变量都应进入主项目正式目录。
### 2.2 以前端视觉风格对齐主项目为主

含义。- 主项目提供统丢页面布局、导航”视觉风格”组件风格语訢。- 。food 模块的业务交互流，优先保。`foodidentity` 的闭环”辑。
直接影响：- 不建议简单保。`foodidentity` 原页面样式。- 也不建议只保留主项目现有 food 页交互。- 正确方式是：
  用主项目的视觉模板重。`foodidentity` 的功能页靃69。
### 2.3 迁移目标不是“兼容旧 food 模块”，而是“用 foodidentity 替换旧”路。
含义。- 。food 页面、旧 nutrition 查询方式、旧手工记录流程，都不应成为新方案的核心约束。- 如果旧方案与 `foodidentity` 冲突，应优先保留 `foodidentity` 的完整”。- 但替换完成后，正式代码归属权应回到主项目，不应形成”主项目 + foodidentity 子项目”双轨并存。
### 2.4 foodidentity 是迁移来源，不是长期运行依赖

含义。- `foodidentity` 的职责是提供产品原型、业务流程”接口语义”数据库设计参”。- 丢旦核心能力完成迁移，主项目应可以脱离 `foodidentity` 独立运行。
直接影响：- 不应通过复制构建产物、反向代理到 `foodidentity` 服务、跨目录 import 业务代码等方式完成所谓”集成”。- 不应让主项目在部署时要求 `foodidentity` 目录继续存在。- 文档、代码”配置都应以“最终可删除 `foodidentity` 目录”为验收标准。
## 3. foodidentity 的真正核心功能盘。
从代码结构看，`foodidentity` 值得迁移的不是”整个目录下扢有内容”，而是以下 5 个核心能力层。
### 3.1 图像识别能力

位置。- `foodidentity/api/routes/recognize.ts`
- `foodidentity/api/utils/stepfun.ts`

作用。- 接收用户上传的食物图片。- 调用 Stepfun 多模态模型进行识别。- 通过强约束提示词让模型只返回食物名数组。- 对非标准 JSON 返回做容错处理。
判断：- 这是 food 模块的核。AI 能力。- 必须保留。- 这是未来 food 模块区别于普通营养查询页的关键点。
### 3.2 食物名称标准化与匹配能力

位置。- `foodidentity/api/utils/foodMatch.ts`
- `foodidentity/api/utils/text.ts`

作用。- 将识别得到的自然语言结果映射到系统内部食物实体。- 通过别名、文本归丢化”包含关系”Jaccard、编辑距离等规则进行匹配。
判断：- 这是识别结果落库的关键桥梁。- 必须保留。- 如果没有这层，识别能力无法稳定转化为结构化业务数据。
### 3.3 结构化食物库

位置。- `foodidentity/db/init.sql`
- `foodidentity/api/routes/foods.ts`

作用。- 提供系统内部 `foods` 基础数据。- 支持按分类”关键词、批。ID 查询。- 为识别匹配”营养计算”前端食物”择提供统一数据源。
判断：- 这是 `foodidentity` 区别于”临时查外部公共库”的关键设计。- 应作为正式模块的基础设施保留。- 即使后续扩容数据源，也应沿用这类内部食物主表设计。
### 3.4 膳食记录模型

位置。- `foodidentity/api/routes/meals.ts`
- `foodidentity/db/init.sql`

作用。- 通过 `meal_records + meal_items` 管理餐次记录。- 支持早餐、午餐”晚餐”加餐等场景。- 支持按餐编辑、覆盖保存”删除”按天汇总。
判断：- 这是 foodidentity 的核心业务模型。- 应完整保留，不建议降级成平铺记录模型。- 这一模型天然适合后续做饮食管理”摄入统计”目标跟踪。
### 3.5 朢小产品闭环前。
位置。- `foodidentity/src/pages/Home.tsx`
- `foodidentity/src/pages/Meal.tsx`
- `foodidentity/src/components/meal/*`

作用。- 首页查看今日摄入概览。- 按餐进入记录页。- 搜索、分类”择食物。- 拍照识别后加入餐次。- 调整克数并保存。
判断：- 这套交互不是 demo 噱头，”是完整产品雏形。- 它应该成为未来主。food 模块的交互原型。- 霢要重做样式，但不应推翻流程。

## 6. 迁移可行性分。
## 6.1 为什么现在更可行

在当前新前提下，可行性更高，原因有三点：

1. 不再霢要兼容旧后端接口。2. 不再霢要兼容旧数据库模型。3. `foodidentity` 本身已经是完整闭环，不是零散算法集合。

## 6.2 主要工程工作是什。

## 7. 迁移合理性分。
在你当前给出的边界下，迁移不仅可行，而且比上丢种”路更合理。
### 7.1 合理性的核心原因

- `foodidentity` 已经定义清楚“food 模块应该怎么工作”。- 主项目只提供 UI 风格模板，不再反向制约业务设计。- 这样能避免把丢个完整闭环拆碎后塞进旧结构，导致产品体验变形。
### 7.2 为什么不应再用”旧模型优先”的思路

如果仍以主项目原有后端和数据库为先，会出现几个问题：

- `foodidentity` 。meal 模型会被压扁。- 识别能力会变成零散附加接口，而不是主流程。- 前端只能做局部补丁，难以形成真正的饮食管理模块。
而现在你已经明确放弃这种约束，这本身就是正确方向。
