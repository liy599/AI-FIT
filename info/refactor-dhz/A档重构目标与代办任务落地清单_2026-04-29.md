# AI-FIT A档重构目标与代办任务落地清单（refactor/a-grade-hardening）

- 文档日期：2026-04-29
- 适用分支：`refactor/a-grade-hardening`
- 对齐标准：`info/requirement-dhz/essential_requirement_refined.md`
- 使用方式：按阶段执行并在每项前打勾；每个阶段完成后提交一次 git commit。

## 1. 总目标（Definition of Done）

- [ ] 满足课程 A 档核心要求：需求匹配、架构清晰、质量达标、文档闭环。
- [ ] 消除高风险安全项（密钥、路径越权、调试配置）。
- [ ] 建立可复现的评测流程（用户手册 + 测试计划 + UAT清单）。
- [ ] 完成工程化关键能力（数据库迁移、可扩展限流、认证会话治理）。
- [ ] 项目达到“可演示、可验收、可维护”的工业化交付基线。

## 2. 里程碑与阶段计划

## M1：P0 阻断项清零（目标 2-3 天）

- [ ] P0-1 示例环境文件去敏与密钥治理
  - 目标：仓库不出现真实密钥；仅保留占位符。
  - 主要文件：`backend/.env.example`、根目录 `.env.example`
  - 验收：全文检索无真实密钥模式；文档说明“部署前必须替换”。

- [ ] P0-2 上传路径校验加固
  - 目标：消除 `startswith` 路径前缀绕过风险。
  - 主要文件：`backend/app/utils/upload_access.py`
  - 验收：改为 `Path.resolve()` + `relative_to()` 目录包含校验；补充对应测试。

- [ ] P0-3 Debug 配置硬化
  - 目标：默认非调试；仅开发环境可显式开启。
  - 主要文件：`backend/run.py`、`backend/app/config.py`
  - 验收：默认启动 `debug=False`；环境变量可控。

- [ ] P0-4 文档闭环骨架（验收必需）
  - 目标：提供可执行的用户与评测文档。
  - 新增文件：`docs/USER_MANUAL.md`、`docs/TEST_PLAN.md`、`docs/UAT_CHECKLIST.md`
  - 验收：评审可按文档独立完成全流程走查。

## M2：P1 工程化能力补齐（目标 4-6 天）

- [ ] P1-1 数据库迁移体系
  - 目标：从 `db.create_all()` 过渡到版本化迁移。
  - 主要文件：`backend/app/__init__.py`、新增 `backend/migrations/*`
  - 验收：支持 `upgrade/downgrade`；发布流程可复现。

- [ ] P1-2 分布式限流（多实例可用）
  - 目标：限流后端可切换内存/Redis，生产默认 Redis。
  - 主要文件：`backend/app/utils/rate_limit.py`、`backend/app/config.py`
  - 验收：策略可配置；多实例下限流语义一致。

- [ ] P1-3 JWT 生命周期治理
  - 目标：补齐 refresh token + 失效机制（黑名单或版本戳）。
  - 主要文件：`backend/app/routes/auth.py`、相关 model/service
  - 验收：登录、刷新、登出、改密后旧 token 失效行为可验证。

## M3：P2 评分增强项与稳定性提升（目标 2-4 天）

- [ ] P2-1 设计模式显式落地与文档化
  - 目标：在关键模块应用并标注模式用途。
  - 建议模式：
    - 工厂模式：姿态分析器/报告生成器创建
    - 策略模式：限流、阈值规则、报告生成策略
    - 门面模式：前端 API 统一入口
    - 模板方法：评测流程框架
  - 验收：代码中有清晰边界；`ARCHITECTURE.md` 更新“模式与收益”。

- [ ] P2-2 性能与可用性证据补齐
  - 目标：形成最小性能/稳定性证据链。
  - 输出：关键接口响应时间记录、错误恢复路径、已知限制说明。
  - 验收：`docs/TEST_PLAN.md` 有实际结果与结论。

- [ ] P2-3 部署与演示一致性
  - 目标：减少评审环境偶发问题。
  - 主要文件：`docker-compose.yml`、`scripts/dev.ps1`、`info/docs-dhz/RUNBOOK.md`
  - 验收：新机器按步骤可一键启动并完成演示。

## 3. 任务看板（执行顺序）

- [ ] Step 1：建立 `docs/` 三件套并填充首版内容。
- [ ] Step 2：完成 P0-1/P0-2/P0-3 的代码改造与测试。
- [ ] Step 3：提交 `chore(p0): harden security baseline and acceptance docs`。
- [ ] Step 4：接入 DB migration 并移除生产路径 `create_all` 依赖。
- [ ] Step 5：落地 Redis 限流策略并补齐配置。
- [ ] Step 6：实现 JWT refresh + revoke 机制。
- [ ] Step 7：整理设计模式说明与架构文档更新。
- [ ] Step 8：完成 UAT 彩排，补齐测试记录与问题闭环。

## 4. 每阶段提交规范（建议）

- P0 提交：`chore(p0): harden security baseline and scaffold acceptance docs`
- P1 提交：`feat(p1): introduce db migrations, distributed rate limit and jwt lifecycle`
- P2 提交：`refactor(p2): apply design patterns and finalize production readiness docs`

## 5. 风险与回退策略

- [ ] 变更前打标签：`git tag backup/pre-a-grade-hardening-2026-04-29`
- [ ] 每一项高风险改动先加测试再改实现。
- [ ] 若迁移脚本失败：优先修复 migration，不回退到 `create_all`。
- [ ] 若 Redis 不可用：开发环境 fallback 内存策略，生产环境强制告警。

## 6. 验收出口（最终勾选）

- [ ] 核心流程（登录、主业务、关键接口）可用且无严重 bug。
- [ ] 安全项无高危问题，配置符合最小安全基线。
- [ ] 文档可指导第三方独立部署、使用、评测。
- [ ] 测试结果与用户手册一致，UAT 流程顺畅。
- [ ] 架构清晰、模块边界明确、具备可扩展改造路径。
